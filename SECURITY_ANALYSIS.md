# Анализ безопасности DailySales

> Дата: 26 июня 2026  
> Статус: зафиксировано для последующей проработки

---

## ✅ Что уже реализовано на хорошем уровне

### Аутентификация
- **Пароли**: PBKDF2-SHA256, 390 000 итераций + случайная соль
- **2FA (TOTP)**: Google Authenticator / любое TOTP-приложение. Коды восстановления хранятся как SHA-256 хэши
- **Telegram-вход**: HMAC-SHA256 по токену бота — стандарт Telegram
- **Сессии**: JWT HS256, 7 дней, cookie с флагами `HttpOnly + Secure + SameSite=Lax`

### Защита от типовых атак
- **CSRF**: токен вида `nonce.HMAC(session_jwt)` — привязан к конкретной сессии, на каждый запрос новый. Проверяется и в form-поле, и в `X-CSRF-Token` заголовке
- **SQL-инъекции**: практически везде параметризованные запросы; f-строки с SQL только для имён таблиц/колонок, не пользовательского ввода
- **XSS**: Jinja2 с авто-эскейпингом по умолчанию; `| safe` используется точечно
- **Path traversal**: при выдаче файлов доказательств оплаты — проверка абсолютного пути prefix-ом

### Заголовки безопасности
```
Content-Security-Policy: default-src 'self' + строгий allow-list
Strict-Transport-Security: 31536000 (HSTS)
X-Frame-Options: SAMEORIGIN
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

### Изоляция клиентов (мультитенантность)
- Каждая организация — отдельный SQLite-файл `data/tenants/org_*.db`
- JWT содержит путь к конкретной БД организации
- Смена организации супер-админом — новый JWT, не «дырка» в сессии

### Мониторинг
- При входе с нового IP — уведомление пользователю в Telegram
- Таблица `admin_audit_log` — все действия супер-админа с IP, временем, деталью
- Ограничение частоты запросов на все auth-эндпоинты (persistent, выживает перезапуск)

### Платежи
- Никаких PAN/CVV — не храним карточные данные
- Доказательства оплаты — рандомизированные имена файлов, доступ только своему автору или супер-админу
- Идемпотентность выдачи подписок по `payment_request_id`

## ⚠️ Реальные риски — по приоритету

### 🔴 Критично для корпоративных клиентов

**1. Нет шифрования данных на диске (Encryption at Rest)**

Все SQLite-файлы (`data/*.db`) хранятся открытым текстом на файловой системе Amvera:
- Если хостинг скомпрометирован → все данные всех организаций читаемы без пароля
- Бэкапы в `data/backup/` — тоже не зашифрованы
- Google OAuth токены в `integration_connections` — plaintext в БД

Для регулируемых отраслей (ФЗ-152, медицина, госструктуры) это де-факто блокер.

**2. Персональные данные без инфраструктуры соответствия (ФЗ-152 / GDPR)**

Хранится: ФИО, телефон, email, IP-адреса, переписка в чате, данные о продажах, привязанные к конкретным людям. При этом:
- Нет механизма «удалить данные пользователя» (право на забвение)
- Нет журнала передачи ПДн третьим лицам
- Переписка в чате хранится бессрочно (нет настраиваемого retention)
- Нет экрана согласия на обработку ПДн при регистрации

---

### 🟡 Важно, но решаемо

**3. Rate limiter "fails open"**

Если `rate_limits.db` недоступна — ограничитель пропускает запросы. При сбое хранилища брутфорс-защита отключается. Нужно fail-closed: при ошибке — блокировать.

**4. `unsafe-eval` + `unsafe-inline` в CSP**

Alpine.js + Chart.js с inline-конфигами требуют оба флага. Снижает защиту от XSS. Решается переходом на Alpine CSP-build или выносом конфигов Chart.js в отдельные `.js` файлы.

**5. Расхождение путей подтверждения оплаты**

Бот делает дополнительные обновления в `main.db` при подтверждении, веб — нет. Если суперадмин подтвердит оплату через веб-панель, план организации может не обновиться.

**6. Ротация JWT-секрета**

Если `SECRET_KEY` утечёт — нет механизма server-side logout / token revocation (JWT stateless по природе). Инвалидация всех сессий требует смены ключа и рестарта.

**7. ✅ `create_subscription_addon` — идемпотентность реализована** _(2026-06-26)_

`UNIQUE INDEX idx_addons_payment` (partial, WHERE payment_request_id IS NOT NULL) + pre-check SELECT + race-recovery в except. Все вызовы в `confirm_payment_request` передают `payment_request_id`. Тест в `test_imports.py` строки 220–228.

### 🟢 Известные осознанные компромиссы

| Решение | Почему так |
|---|---|
| SQLite вместо PostgreSQL | Простота деплоя, изоляция per-org. Потолок ~30 платящих орг. |
| YooKassa без webhook, с polling | Работает, но +latency при проверке |
| `unsafe-eval` в CSP | Alpine.js 3 требует. Без него вся JS-интерактивность мертва |
| Google OAuth токены plaintext | Server-side only, нет публичного access path |

## 📋 Итоговый вердикт по сегментам клиентов

| Сегмент | Статус | Главный стоппер |
|---|---|---|
| МСБ без строгих требований | ✅ Можно продавать | — |
| Сети / Франшизы (50–200 чел) | ✅ С оговорками | Нет шифрования at-rest; уведомить письменно |
| Компании с требованиями ФЗ-152 | ⚠️ Нужна доработка | Шифрование at-rest + политика обработки ПДн |
| Госструктуры / медицина | ❌ Не готово | Шифрование, сертификация, on-premise |
| Международные (GDPR) | ❌ Не готово | Право на забвение, DPA, локализация данных |
