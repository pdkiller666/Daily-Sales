# Аудит проекта Daily Sales — 08.07.2026

Метод: параллельный код-аудит 12 доменов силами read-only исследователей + ручная
верификация самых громких находок (грепы по реальному коду). Часть находок из
первого прохода оказалась ложной тревогой — это учтено ниже explicit.

## Как читать этот отчёт

- **Подтверждено** — лично проверено гит-грепом/чтением кода, реальная проблема.
- **Похоже на ложную тревогу (проверено)** — заявлено агентом, но при проверке
  оказалось безопасно (объяснение почему).
- **Не проверено вручную** — правдоподобная находка агента, стоит проверить перед
  тем как чинить; список сгруппирован по модулям для точечной проверки.

## 1. Уже проверено и снято (ложные тревоги первого прохода)

Несколько доменов независимо друг от друга подняли одни и те же паттерны как
"критические". Все три при ручной проверке оказались безопасны:

- **"SQL-инъекция через f-string в UPDATE ... SET {col}"** (database.py:
  `update_org_role`, `update_department`, и похожие в 5901+): имена колонок —
  захардкоженные литералы в коде (`"color = ?"`, `"base_role = ?"` и т.п.), а не
  пользовательский ввод. Значения всегда идут через `?`-плейсхолдеры. Инъекции
  нет — паттерн стандартный для динамического "частичного UPDATE".
- **"IDOR через подмену org_db в JWT-куке"**: `org_db` зашит в подписанный JWT
  (`web/auth.py: create_session_token` → `jwt.encode(..., _SECRET, ...)`), любое
  изменение payload ломает подпись при `jwt.decode`. Сменить организацию может
  только `super_admin` через `switch_org`, и то с проверкой `is_active=1` и CSRF.
  Подмена невозможна без знания `_SECRET`.
- **"Race condition в списании остатков (read-then-write)"**: реальный код
  использует атомарный `UPDATE inventory SET quantity = quantity - ?` (SQLite
  сам сериализует), не read-modify-write на стороне Python. Гонки нет.
- **"CSRF отсутствует в subscription.py/org_structure.py/tasks.py"**: на самом
  деле `verify_csrf_token` реализован практически на каждом POST в этих файлах
  (проверено грепом — десятки вызовов). Похоже, агенты не всегда долистывали
  файл до конца функции.

Общий вывод: код уже прошёл несколько раундов security-аудита (это подтверждает
и `.agents/memory` — `security-audit.md`, `security-2fa-audit.md`), поэтому
поверхностные грепы по "опасным паттернам" дают много ложных срабатываний.
Архитектура "одна SQLite-база на организацию" сама по себе исключает большинство
классических межорганизационных IDOR через перебор ID — чужие данные физически
лежат в другом файле, к которому нет доступа без подписанного `org_db` в токене.

## 2. Подтверждено — реальные, но некритичные находки

- **`web/routes/api.py: push_subscribe`** не делает Origin-check, который есть в
  соседней `push_unsubscribe` (та же логика в разных местах разошлась).
  Комментарий в коде объясняет, что для JSON+samesite=lax CSRF не обязателен —
  это разумно, но добавить ту же Origin-проверку для консистентности дёшево и
  не помешает defense-in-depth.

## 3. Не проверено вручную — кандидаты на точечную проверку

Ниже — находки агентов, которые звучат правдоподобно для проекта такого масштаба,
но я не успел лично прочитать каждую строчку (файлы по 50–200 КБ). Рекомендую
проверять точечно, когда будете трогать соответствующий модуль, а не чинить всё
одним махом.

### Права доступа внутри организации (не межорганизационные — там архитектура защищает)
- `web/routes/salary.py` — убедиться, что обычный `user` не может запросить
  чужую зарплату, подставив `user_id` в параметрах (сверка `sub`==`user_id` для
  не-админов).
- `web/routes/contests.py`, `web/routes/plans.py` — `get_contest/update_contest`,
  `update/delete/toggle` для планов — стоит явно свериться, что методы БД (или
  роут) проверяют принадлежность записи не только по org_db-файлу, но и что
  ID реально существует в открытой базе (обычно это само собой верно за счёт
  per-org БД, но стоит один раз пройти глазами).
- `web/routes/integration.py` (`integration_toggle/delete/move_exports`) —
  аналогично сверить, что `conn_id`/`cid` ищутся в контексте текущей org_db, а
  не в общей таблице без фильтра.
- `web/routes/clients.py`, `web/routes/services.py` — упомянутые f-string куски
  в поиске/фильтрации (не UPDATE) — если это динамические WHERE по
  пользовательскому вводу (а не whitelisted-поля), проверить параметризацию
  отдельно, т.к. паттерн УЖЕ отличается от подтверждённо-безопасного `SET {col}`.

### Идемпотентность и конкурентность
- `web/routes/chat.py` — AI-лимиты (`check_and_increment_ai_for_org`) при быстрой
  серии запросов — проверить, атомарен ли инкремент (транзакция/`UPDATE ... SET
  used = used + 1 WHERE used < limit` вместо read-then-write).
- `web/routes/motivation.py: motivation_set_category` — цикл обновления ставок
  по категории без единой транзакции — при сбое посередине часть товаров
  останется со старыми ставками.
- `tenant_manager.py: delete_organization` — удаление файлов БД и очистка
  main.db не атомарны; при сбое возможны "осиротевшие" файлы/записи.

### Обработка ошибок / незавершённый функционал
- `task_automation.py` — сетевые вызовы (`_tg_send`, `_push_send`) через daemon-
  треды с `except: pass` — сбои Telegram/Push API молча теряются.
- `plan_notifications.py` — три места с пустым `except Exception: pass` при
  рассылке — блокировка бота пользователем не логируется, диагностировать
  недоставку сложно.
- `web/routes/products.py: _get_user_label_size/_save_user_label_size` —
  широкий `except Exception: return "58x40"` может маскировать реальные ошибки
  БД.
- `absence_handlers.py` — дублирование логики лимитов отсутствий с
  `web/routes/absences.py`; при правке одной стороны легко забыть другую (уже
  встречалось в проекте — см. `.agents/memory/salary-paid-absences.md`).

### Качество кода (не баги, но снижает поддерживаемость)
- `database.py` — файл 930 КБ (~19k+ строк), огромное количество `except
  Exception: pass` — усложняет диагностику тихих сбоев схемы.
- Дублирование мелких хелперов между вебом и ботом: `_get_display_name` /
  `_name_from_org` (auth_routes.py/email_auth.py), `_get_user_db_id`
  (notifications.py/plans.py/rankings.py).
- Разбросанные по файлам хардкоженные пути `data/main.db`, `data/shop_bot.db`
  вместо единой точки конфигурации.

## 4. Что сделано хорошо (подтверждено)

- **Изоляция арендаторов** — архитектура "SQLite-файл на организацию" реально
  исключает целый класс межорганизационных утечек by design.
- **Подписанные JWT-сессии** с revocation по `jti`, PBKDF2-SHA256 (390k
  итераций) для паролей, строгий nonce-based CSP без `unsafe-inline`.
- **CSRF** внедрён системно и широко (не выборочно, как показалось в первом
  проходе).
- **Атомарные операции со складом и деньгами** (`quantity = quantity ± ?`,
  идемпотентные payment/referral паттерны — уже задокументировано в памяти
  агента: `money-grant-paths.md`, `referral-bonus-grant.md`).
- **Событийный планировщик** (`_sched_index`) вместо полного обхода баз каждую
  минуту — заметная оптимизация для десятков организаций.
- **Зрелое тестовое покрытие критических путей**: импорт-аудит 50 модулей,
  Playwright-smoke с проверкой CSP/Alpine, регресс-тесты на конкретные баги
  (VAPID, слияние отсутствий, двойной `callback.answer()`).
