# Кросс-модульные действия гейтить по доступности ЦЕЛЕВОГО модуля

**Правило:** если модуль A создаёт сущность в модуле B (пример: форма задачи с чек-боксом
«Создать тему в чате» → `db.add_chat_topic`), то и UI-чекбокс, и бэкенд-обработчик обязаны
перепроверять доступность B той же логикой, что и собственная страница B. Для чата это
`_get_chat_min_plan() != 'Отключён'` И `has_module(tg, 'chat')` (helper `_chat_available()` в
`web/routes/tasks.py` зеркалит `chat_page`).

**Why:** чек-бокс «Создать тему в чате» показывался всегда и бэкенд `tasks_new_post` создавал тему
без проверки → тема рождалась в отключённом/неоплаченном чате, а ссылка «Обсудить в чате»
(`/chat?topic=<id>`) вела на заблокированный модуль. Гейт страницы B сам по себе не спасает —
сущность уже создана «вслепую».

**How to apply:**
- Бэкенд: условие создания включает доступность целевого модуля (не только наличие флага из формы).
- UI: и форма-источник, и место отображения ссылки (`detail.html`) гейтятся флагом
  `chat_available|default(false)` (передаётся в ctx обоих маршрутов).
- Helper делает локальный импорт `from web.routes.chat import ...` — циклического импорта нет
  (chat.py не импортирует tasks).

## Связь tasks↔chat (справочно)
- `tasks.linked_chat_topic_id` → `chat_topics.id`; ссылка на детали задачи `/chat?topic=<id>`.
- `chat_page` устойчив к несуществующему `topic`: fallback на «Общий» (valid_ids проверка), краха нет.
- `delete_task` НАМЕРЕННО не удаляет связанную тему — история обсуждения сохраняется
  (автоочистку не вводить без отдельной retention-политики).
- Бот-сторона задач (`tasks_handlers.py`) НЕ создаёт `linked_chat_topic_id` — вектор только веб-форма.
