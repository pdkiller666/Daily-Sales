---
name: Packages (subscriptions) integration lessons
description: Durable pitfalls when integrating a package/subscription-style entity into kassa, reports, refunds, and bot layers alongside existing product/service sales.
---

- No formal kassa/shift/Z-report entity exists in this codebase — revenue is live-aggregated straight from sales-like tables at query time. "Integrate into kassa/reports" means adding the same aggregation points (dashboard cards, sales feed, report KPIs, daily chart), not building a ledger.
- Any new revenue-aggregation block added to a scoped report route must apply the SAME shop/user scope filter as the sibling blocks in that route (and exclude soft-refunded/void rows) — copy-pasting an existing sibling block's SQL without also copying its scope-filter branch silently leaks cross-shop revenue data to scoped users. Treat this as a security bug, not a display nit, and audit every new metric block added to an existing scoped report for scope-filter parity with its neighbors.
- **Refund math for any entity with a mutable running total (remaining balance, visits, etc.) must snapshot the immutable original basis at creation time.** Computing a per-unit rate from the *current* (already-reduced) total on each repeated partial refund compounds errors and can make cumulative refunds exceed the original payment. Fix pattern: snapshot `original_*` once at creation; every refund computes off that constant; cap cumulative refunded amount to the original payment so the final/full refund pays exactly the remainder.
- The same compounding trap applies to proportional reversal of any linked value (e.g. commission): always recompute from the immutable original and the cumulative refunded ratio, never by repeatedly scaling the already-reduced current value.
- A migration backfill for a newly-added "immutable original" column must reconstruct history-aware values for legacy rows (original = current + already-consumed-per-history-table), not just copy the current value — otherwise legacy partially-modified records get a silently wrong permanent snapshot with no runtime fallback.
- `db_utils.get_db()` returns an `AsyncDatabase` wrapper. Calling a method like `get_connection()` directly on it without unwrapping does not raise immediately — it returns an unawaited coroutine (only a RuntimeWarning), which then fails downstream with a generic error easily swallowed by a broad except. Bot/handler code needing a raw sync connection must go through the wrapper's underlying sync object, not call wrapped methods directly.
- For any read-then-conditionally-write business function on a mutable running total (refunds, balances, etc.) that is called from a request path without an outer transaction guarantee, wrap the whole read+compute+write in one `BEGIN IMMEDIATE ... COMMIT/ROLLBACK` on the raw sqlite3 cursor (isolation_level=None + manual BEGIN, restore isolation_level in `finally`) — otherwise concurrent calls can both read the same pre-write state and both apply their change, double-counting/overpaying. Verified with a real multi-thread test, not just sequential logic review.
- A "refund all remaining" branch must cap against the value of only the *still-unused* portion (ceiling excluding already-consumed units), never against the full original payment — otherwise a full-remainder refund on a partially-used item overpays for units the customer already consumed. Use the ceiling only to correct rounding drift on the final partial refund, not as the refund amount itself.
