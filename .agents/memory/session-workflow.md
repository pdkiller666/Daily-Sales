## ⚑ ПРАВИЛО 0 — ОБЯЗАТЕЛЬНО ПОСЛЕ КАЖДОЙ СЕССИИ (любой, даже маленькой)

**Три шага без исключений:**
1. **Аудит** — `python test_imports.py` (0 ошибок), синтаксис-чек `.py`-файлов
2. **Тесты** — убедиться, что приложение поднимается без ошибок (workflow running, HTTP 200)
3. **Деплой** — `bash deploy.sh "описание"` → GitHub + Amvera

Не ждать команды от пользователя. Делать сразу после завершения работы.

**Why (инструкция пользователя 2026-06-26):** «после каждой сессии аудит, тесты и деплой» — жёсткое требование, нарушение ведёт к расхождению production и main.

## Правило 1 — Полный чеклист после большой сессии (фича / серьёзный фикс)

1. **Аудит импортов**: `python test_imports.py` — должно быть 0 ошибок
2. **Синтаксис-чек**:
   ```python
   python -c "import ast, os; errors=[]; [errors.append(f'{fn}: {e}') for fn in os.listdir('.') if fn.endswith('.py') and not fn.startswith('test_') for e in [None] if not (lambda: (ast.parse(open(fn).read()), None)[1])()]; print('✅ OK' if not errors else '\n'.join(errors))"
   ```
3. **Обновить AGENT_HANDOFF.md**: добавить секцию текущей сессии с тем, что сделано, хэши деплоя
4. **Обновить PROJECT_MAP.md** (если добавлены новые роуты/методы/таблицы)
5. **Обновить UI_MAP.md** (если изменился интерфейс бота/веба)
6. **Создать фрагмент новости** (ОБЯЗАТЕЛЬНО при любой пользовательской фиче): положить `web/changelog.d/<уникальное-имя>.md` (например `task-42.md`) с одной строкой-новостью с точки зрения пользователя. НЕ редактировать `web/changelog.py` руками — его собирает `scripts/build_changelog.py` автоматически при деплое (фрагменты → запись версии + бамп `CURRENT_VERSION` + AI-полировка). Уникальные имена фрагментов = нет конфликтов слияния у параллельных агентов-задач. Подробности — `web/changelog.d/README.md`.
7. **Деплой**: `bash deploy.sh "описание изменений"` → GitHub + Amvera
8. **Обновить MEMORY.md**: если было что-то нетривиальное — добавить в индекс

**Why:** deploy.sh автоматически обновляет хэши и номер сессии в AGENT_HANDOFF.md, но содержательную часть (что именно сделано) агент должен дописать сам перед деплоем.

**How to apply:** Каждый раз после завершения реализации фичи, перед тем как ответить пользователю «готово».

## Правило 2 — Каждые 5 деплоев: актуализация трёх репозиториев

Счётчик деплоев хранить в уме (или смотреть в AGENT_HANDOFF.md — строка «Последний деплой»).

**Процедура актуализации:**
1. Проверить последний коммит на GitHub: `git ls-remote origin refs/heads/main`
2. Проверить последний коммит на Amvera: `git ls-remote amvera refs/heads/master` (из `/tmp/amvera-deploy`)
3. Сравнить хэши из AGENT_HANDOFF.md с реальными
4. Если расхождение — форс-деплой: `bash deploy.sh "sync: актуализация репо"`
5. Убедиться что в Replit (local) нет несохранённых изменений

**Why:** deploy.sh использует --force push на Amvera, что может создать расхождения если кто-то пушил напрямую. GitHub может уйти вперёд если AGENT_HANDOFF.md пушился отдельно.

## Правило 3 — После каждого слияния фоновой задачи (task merge)

**Порядок немедленно после merge-чекпоинта:**
1. `git --no-optional-locks log --oneline -5` — убедиться, что мёрдж-коммиты видны HEAD
2. `git --no-optional-locks status --short` — рабочая директория должна быть чистой
3. `bash deploy.sh "feat: ..."` — задеплоить ВСЕ накопившиеся мёрджи одним коммитом
4. Проверить в выводе: `Amvera verify: ✅ remote hash совпадает`

**Why:** Фоновые агенты коммитят в main, но на Amvera (production) изменения попадают только через deploy.sh. Без немедленного деплоя production отстаёт от main на N мёрджей — пользователь не видит готовые фичи.

**How to apply:** При каждом `checkpoint_created trigger_reason="A task was merged"` в automatic_updates — сразу запустить процедуру выше, не ждать следующего сообщения от пользователя.

## Важные файлы md-агента

| Файл | Назначение | Деплоится на Amvera |
|------|-----------|-------------------|
| `AGENT_HANDOFF.md` | Полный контекст для агента, история сессий, gotchas | ❌ только GitHub |
| `PROJECT_MAP.md` | Роуты, методы БД, callback-схемы | ❌ только GitHub |
| `UI_MAP.md` | Карта интерфейса бота, все callback_data | ❌ только GitHub |
| `README.md` | Публичная документация | ❌ только GitHub |
| `.agents/memory/` | Долгосрочная память агента | ❌ .local не деплоится |

**How to apply:** При добавлении нового роута — обновить PROJECT_MAP.md раздел 11 (web routes). При изменении интерфейса — добавить запись в UI_MAP.md раздел «История изменений».
