# Мультифайл во вложениях ЛС

Бэкенд и фронт-инпут поддерживали мультифайл в ЛС ИЗНАЧАЛЬНО (`dm_send`
принимает `List[UploadFile]` → `add_dm_files`; `_fmt_dm` отдаёт `files[]`;
инпут `multiple` + `dmAttachedFiles`/`onDmFileChange`/`dmRemoveFile` + send-loop
+ чипы-превью). Реальные пробелы были только в **рендере полученных** файлов.

## Два пробела (исправлены)
1. **DM-пузырь рендерил только ОДИН файл** (`m.file_url`/`m.file_name`).
   Исправление: `x-for` по `m.files` + legacy single-file fallback
   (`m.has_file && (!m.files || !m.files.length)`) — точное зеркало группового пузыря.
2. **Клиентский WS-обработчик входящих DM** (`data.type==='message'`) НЕ переносил
   `data.files` в pushed-объект → мультифайл, пришедший по WS, деградировал до
   первого файла. Исправление: `files: data.files || []`.

## Почему пути доставки разные (важно при будущих правках)
- **WS-путь** (получатель) строит объект сообщения ВРУЧНУЮ по полям payload —
  любое новое поле сообщения надо добавлять И в `_fmt_dm` (HTTP), И в этот
  ручной WS-push, иначе фича работает по HTTP, но молча ломается в реальном времени.
- **HTTP-ответ отправителю** и **загрузка диалога** идут через `_fmt_dm` → `files[]`
  уже есть, отдельных правок не требуют.
- **Оптимистичная отправка** по WS — только текст (файлы всегда идут по HTTP),
  поэтому в оптимистичном пуше `files: []` корректно.

**Правило:** группа и ЛС зеркалят фичи, но у ЛС есть РУЧНОЙ WS-сборщик входящего
сообщения — он не использует серверный форматтер, поэтому любое поле пузыря
надо дублировать в нём явно.
