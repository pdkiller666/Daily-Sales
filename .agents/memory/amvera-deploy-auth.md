description: Две ловушки прямого git-push на Amvera, из-за которых фикс молча НЕ доехал до прода.
---

## Ловушка 1: учётные данные в URL обязаны URL-энкодиться

`deploy.sh` пушит на `https://USER:PASS@git.msk0.amvera.ru/...`. Если `AMVERA_PASS`
(или USER) содержит спецсимвол (`:`, `@`, `/`, `#`, пробел) — git разбирает URL
неверно:
- `:` в пароле → «URL rejected: Port number was not a decimal number» (текст после
  `:` принят за порт);
- `@` → строка обрывается, неверный хост.

**Решение:** перед вставкой в URL кодировать оба компонента через
`urllib.parse.quote(..., safe='')`. Реализовано в `deploy.sh` (переменная
`AMVERA_REMOTE_URL`).

**Why:** пароль аккаунта Amvera может быть ротирован пользователем на значение со
спецсимволами; старый код вставлял raw → auth/URL ломались.

## Ловушка 2: упавший push не должен превращаться в «нет изменений»

Старый `deploy.sh` определял «есть ли что пушить» сравнением рабочих файлов с
**локальным** HEAD. Сценарий потери фикса:
1. Запуск A: коммит создан локально, `git push amvera` упал по auth, `set -e`
   оборвал скрипт.
2. Запуск B: рабочие файлы == локальный HEAD (коммит-то остался) → «нет
   изменений» → push пропущен. На Amvera (прод) фикса нет, хотя GitHub его получил.

**Решение:** решение о push принимать по сравнению `local HEAD` vs `REMOTE_HASH`
(`git ls-remote`). Если различаются (или remote пуст) — пушить, несмотря на
отсутствие новых файловых изменений.

**Why:** был реальный инцидент — фикс зарплаты уехал только на GitHub, на проде
остался старый расчёт; пользователь заметил по скриншоту.

## How to apply

- Любая правка пути push на Amvera → сохранять URL-энкодинг и сверку с remote-хэшем.
- Симптом «GitHub обновлён, Amvera нет» → проверить (а) auth/URL-энкодинг,
  (б) что в `/tmp/amvera-deploy` нет осиротевшего локального коммита, который
  старая логика считала уже задеплоенным.
- Диагностика доступа: `git ls-remote amvera` с URL-энкодед кредами; читает →
  пишет той же авторизацией.
