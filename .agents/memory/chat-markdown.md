# Markdown-форматирование сообщений

Чисто **рендер-тайм** фича: текст хранится сырым, форматируется только при выводе
в общем Alpine-методе `formatMsg(text)` (используется ОБОИМИ типами пузырей —
группы и ЛС, через `x-html`). Бэкенд не трогается — та же модель, что у упоминаний.

Поддержка: `**жирный**`, `*курсив*`/`_курсив_`, `` `инлайн-код` ``,
```` ```блок-кода``` ````, `~~зачёркнут~~`, авто-ссылки `http(s)://…`, `@упоминания`.

## Порядок шагов критичен (XSS + корректность)
1. **`esc()` ПЕРВЫМ** — экранирует `& < > "`. Весь пользовательский HTML
   (`<script>`, `<img onerror>`) обезврежен ДО вставки своих тегов.
2. Код (`` ` `` и ```` ``` ````) прячется в **nonce-плейсхолдеры**, чтобы markdown
   и авто-ссылки не лезли внутрь кода.
3. `**bold**` ДО `*italic*` (иначе `*` съест `**`); затем `~~strike~~`, курсив.
4. Авто-ссылки только `https?://` — **`javascript:` намеренно не линкуется**.
5. Упоминания `@имя`.
6. Restore кода из плейсхолдеров.

## Почему nonce, а не \u0000N\u0000
Плейсхолдер = `\u0001${nonce}${i}\u0001`, где `nonce` — случайный per-call
(`Math.random().toString(36)`). **Why:** фиксированный маркер юзер мог бы
подделать в своём тексте → коллизия при restore (искажённый рендер). Случайный
nonce непредсказуем → подделка невозможна. **How to apply:** restore-regex
строится через `new RegExp` с тем же nonce; любой новый «stash/restore» проход
обязан использовать тот же per-call nonce.

## Границы безопасности (проверено)
- `href` строится из УЖЕ HTML-escaped URL (`"`→`&quot;`, `&`→`&amp;`) → разрыв
  атрибута/инъекция обработчиков не проходит.
- ReDoS-риска нет (regex без катастрофического бэктрекинга, несколько линейных проходов).
- Правка сообщения показывает **сырой** текст (`x-model` на `editText`/`dmEditText`
  из `msg.message`), НЕ отрендеренный markdown — не трогать.
- Поиск (`highlight()`) — отдельная функция, markdown к сниппетам не применяется.
